Workshop · making pictures with Claude

Art by Code and Cursor

Claude can't hold a brush, so every picture it makes comes from one of three routes: writing code that draws, writing code the graphics card runs, or driving a paint program with a mouse it can only see through screenshots. This page walks through each route, why it works, and then asks whether a skill can make the results less predictable.

Route 1 and 2 · code that draws

The build loop

Nobody types the art in. You describe a scene and its rules, Claude writes a program, and the program paints every frame. The useful part is what happens next: Claude opens the result in a headless browser (a real browser with no window, driven by a script), takes screenshots, looks at them, and fixes what looks wrong. Without that last step it is coding blind.

  1. Set the rulesFor example: "No image files. Every motion loops every 60 seconds. Several looks you can switch live." Constraints like these shape the code more than the subject does.
  2. Pick the enginePixel art: a tiny canvas, say 480×270, drawn pixel by pixel in JavaScript and scaled up 4× to fill a 1080p screen. 3D: a shader, a small program the graphics card runs once for every pixel.
  3. Render frozen framesA script opens the page in headless Chromium and saves screenshots of each look. A setting in the address such as ?t=30 freezes the animation at second 30, so every screenshot is repeatable.
  4. Look and fixClaude reads its own screenshots and names problems a person would: edges look jagged, a colour is too dull, small details are too faint to see. Then it edits and renders again.
  5. Check the seamCompare the last frame of the loop with the first. If the jump is no bigger than between ordinary neighbouring frames, the loop is seamless.

A starter prompt to try

Make a single HTML page that draws an animated night harbour with canvas code only, no image files. Every motion must loop seamlessly every 60 seconds. Make each frame depend only on the time t, and add a ?t= setting to the page address that freezes the scene at that second. Then open it with Playwright in headless Chromium, take screenshots at t=0, 20, 40 and 60, look at them, and fix anything that looks wrong. The t=60 shot should match t=0 if the loop is seamless. Repeat until you're happy, and tell me what you changed.

Playwright is a library for controlling a browser from code. Claude Code can install and run it itself. The ?t= setting lets Claude jump straight to any moment instead of waiting in real time. The last two sentences are what turn one attempt into a loop. When we tested this prompt, Claude noticed after the first round that the lighthouse beam pointed the same way in every screenshot, because it turned exactly once every 10 seconds, and fixed it.

The point for students: the model's eyes are screenshots. Anything you want it to judge, it has to be able to render and look at.

Route 1 · code that draws

Seeds and loops

Generative art leans on two ideas. A seed makes randomness repeatable: the same seed gives the same picture every time, a new seed gives a sibling. A whole-number loop makes animation seamless: if every moving thing finishes an exact number of cycles per loop, frame zero and the final frame match. The planet in the next section lets you break that rule: pick "1.37 turns" and press "Jump to the loop seam" to see the snap.

42 
const r = rng(42);   // same seed in, same numbers out

const sunX   = r() * width;    // always the same
const ridges = 7 + r() * 6;    // for seed 42,
const hue    = r() * 360;      // in the same order

Drag the seed back to 42 and the exact same landscape returns. That is how an artist can share "seed 42" instead of a file.

Route 2 · the GPU

Why a whole 3D scene is smaller than a photo

A video stores the answer: the colour of every pixel in every frame. A shader stores the question: given this pixel and this moment, what colour should it be? The graphics card asks that question for all two million pixels of a 1080p screen, sixty times a second, in parallel. Nothing is stored because everything is recomputed. The other half of the trick is that the heavy machinery is already on the student's computer: the browser and the graphics card are the rendering engine. The file only has to describe the scene. It trades storage for computation.

The planet below is drawn by the program printed next to it. There are no models and no textures. The size counter measures the shader's source text as it runs on this page. The few lines of JavaScript that hand it to the graphics card are not counted.

Three tricks that keep it small

      
    
        
  • Ray tracing a sphere is one formula. For each pixel, imagine a ray from the camera through that pixel and ask whether it hits the ball. That is a school quadratic equation: the ray hits when b² − c > 0. No mesh (the triangles 3D models are usually made of) is needed.
    • 
        
  • Detail comes from noise, not images. The swirls in the bands come from a hash: a scrambling formula that turns a position into a number that looks random but is always the same for that position. Nothing needs saving because it can be recomputed.
    • 
        
  • Looks are mostly numbers. A different look is a different set of uniforms, the knobs the page passes into the shader: colours, band counts, light direction. Very different looks, such as an ink drawing or 8-bit pixels, add a short extra branch to the shader. Five looks cost a few kilobytes, not five copies of the art.
    • 
      

      
A fuller scene built this way, with rings, a moon, a gas cloud and five looks, comes to about 25 KB: roughly 15 KB of shader, 8 KB of code that sets up the graphics card and 3 KB of settings for the looks. It is the same idea, just more questions asked per pixel.

    

  


  
  

    
Route 3 · computer use
Painting by cursor

    

      
The third route skips code for the picture entirely. Claude is put in front of JS Paint, a browser copy of MS Paint, and told to make a masterpiece. It only gets what a person would: a screen, a mouse and a keyboard. This is called computer use. Every click or stroke is a tool call (a structured request the model sends out for a program to carry out), and when Claude wants to see the result it asks for a screenshot.

    

    

      
Claude looksAsks for a screenshot (1024×640) or a zoomed-in view of part of the screen.

      
Claude actsReturns a tool call such as left_click_drag with start and end coordinates.

      
Driver movesA small Python program turns that into real mouse input with Playwright, inside Docker (a sealed mini-computer, or container).

      
Result returnsA stroke returns just "OK". Claude chains several strokes, then looks again. The loop repeats until it says it's finished.

What made it work

        
    
          
  • A locked box. The paint program runs in Docker with no network, as a user with no special permissions. Shortcuts that would close or reload the page are refused by the driver.
    • 
          
  • A spending cap. Every screenshot costs tokens, the units the API bills by. The loop counts dollars from each reply, tells Claude to wrap up near the limit and stops before it can go over.
    • 
          
  • Notes instead of memory. After about 30 screenshots the conversation gets heavy, so Claude writes notes to itself and a fresh conversation starts from them with the canvas kept.
    • 
          
  • A timelapse for free. The canvas is saved after every stroke, which doubles as a resume point and the frames of a timelapse.
    • 
        

      

      

        
What students should notice

        
    
          
  • The picture is slow and expensive compared with code. Real runs took tens to hundreds of strokes, 7 to 26 minutes and from under $1 to about $4.
    • 
          
  • The limits of the tool shape the art. Flat colours and hard edges push the model toward bands, silhouettes and simple shapes.
    • 
          
  • Asked for a masterpiece with no other direction, separate runs on different models chose the same subject: a sunset over a mountain lake. That is the "average pick" the next section is about.
    • 
          
  • At the end Claude writes an artist's statement, including what it thinks is weak. Compare its self-critique with yours.
    • 
        

      

    

  


  
  

    
Steering the choices
Can a skill fix taste?

    

      

        
A language model tends to produce what is most likely, given everything it has read. For a creative request, "most likely" means the middle of everything already made: the synthwave sunset poster, the mountain lake, the coffee shop called Common Grounds. It feels right because it's familiar.

        
antialgorithm is a community-made Claude Code skill that tries to push the model off that peak. It doesn't add talent. It adds a procedure:

        
    
          
  1. Name the default. "The default here is X." Then avoid X unless the brief demands it.
    2. 
          
  2. Start from outside. If the request is thin, roll a random starting point (a method, a palette, a setting, a verb) with seed.py. It is the same seed idea from earlier, used to pick ideas instead of pixels, so two people with the same prompt start in different places.
    3. 
          
  3. Give every choice a reason. One sentence, using a fact about this project. Odd for its own sake doesn't count.
    4. 
          
  4. Check the work. check.py renders an SVG and flags text that's cut off, covered, too small or low in contrast.
    5. 
          
  5. Watch your own habits. moves.py logs each main move, so last time's escape doesn't become this time's default.
    6. 
        

      

      

        
        
Where a model's first answer tends to land. The skill's job is to move the answer out of the shaded middle on purpose, for a reason.

      

    

    

      
One comparison we ran

      
Same prompt to two fresh agents: "Design a poster for a music festival as a 400×600 SVG." Without the skill: a purple-to-orange gradient, a striped synthwave sun, a giant centred title, a stacked lineup. With the skill, the agent first wrote down that default, rolled a seed (string and pins, very pale colours, a back yard in Croatia, a lantern), and made the lineup into name tags pegged on washing lines, one line per back yard of one town. check.py caught overlapping tags, which it fixed, but one tag still ended up partly covered.

      
One pair proves very little. The skill's own showcase images were picked from about a dozen runs, and the skill itself warns that its favourite escape (an old, hand-made, printed look) can turn into a new default. That's why the class exercise below runs several prompts.

    

  


  
  

    
Hands on · about 50 minutes
Class exercise: with and without

    

      
Work in pairs. One person is Plain: a normal Claude Code session with no extra skills. The other is Skill: a session with antialgorithm installed. You both give the same prompts, then put the results side by side, labelled, and judge them together. This is not a blind test, so each pair also writes down which side they expect to win before seeing anything; that shows the class its own bias.
