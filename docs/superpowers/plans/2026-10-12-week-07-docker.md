# Week 7 (Running with Docker) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish week 7. Students:
- learn why "works on my machine" isn't enough
- install Docker Desktop (Mac Apple chip, Mac Intel, Windows with WSL 2 and Ubuntu integration)
- have Claude write a `Dockerfile` and `.dockerignore` for their own project on branch `containerize`
- read the Dockerfile line by line
- build the image, run the program and the tests in a container, and compare with their hand-worked example
- check the Dockerfile with week 6's `safe-and-private` reviewer
- merge through a PR

The week also containerizes the deal screener (tag `week-07`) and adds slides, the assignment, instructor notes with a demo script, and checklist rows.

**Architecture:**
- Same approach as weeks 2-6.
- Facts come from Docker's official docs (install pages per platform, system requirements, WSL 2 backend and integration, Docker Desktop licence terms, `docker build` / `docker run` / `-it` / `--rm`, `.dockerignore`, `docker image prune`) and Docker Hub's official `python` image page (tags). All are recorded on a fact sheet with URLs.
- The deal screener's Dockerfile is built and run for real with this machine's Docker Engine.
- The Docker Desktop install on Mac and Windows can't be run here, so it is marked "being tested".

**Tech Stack:** Markdown, Marp (`npm run slides` in Docker), Docker Engine 29.x (dry runs), Docker Desktop (student path), Python 3.9+ standard library for the deal screener, official `python:<version>-slim` image.

**Spec:** `docs/superpowers/specs/2026-10-10-course-design.md`, week 7 row ("Docker: why 'works on my machine' isn't enough, running the app in a container | Containerize their project"). The week 7 design was approved in conversation on 2026-10-12. Decisions:
- Docker Desktop everywhere. On Windows, Docker Desktop for Windows with the WSL 2 backend and Ubuntu integration turned on, and all `docker` commands run in the Ubuntu window.
- Students containerize whatever stack their project uses, with guardrails:
  - an official base image with a pinned version
  - no secrets copied in
  - `.venv`, `node_modules` and `.git` kept out of the image
- The week 6 `safe-and-private` reviewer checks the Dockerfile.
- Assignment: Dockerfile and `.dockerignore` merged by PR, 4 points; screenshots of the tests and the program in the container, 3 points; reflection, 3 points.

## Global Constraints

- Audience: business and non-CS students in week 7. They have Claude Code, git, `gh`, Superpowers and the week 6 reviewers in `.claude/agents/`, plus a merged build and review on `main` of private `semester-project`. Plain language. Every command and prompt is shown exactly and labelled with where to type it: Terminal, the Ubuntu window, PowerShell (only for Windows install steps, if the docs need it), or inside Claude Code.
- Platforms: Mac (Apple chip), Mac (Intel) and Windows (WSL 2 Ubuntu). The install has three labelled paths. After installing, `docker` commands are the same on all three. On Windows they run in the Ubuntu window.
- Docker Desktop licence: state it from Docker's terms page (free for personal, education and small business, under the stated limits). No invented numbers. Requirements (macOS versions, RAM, disk, Windows build, virtualization) come from Docker's pages.
- Image guardrails: an official base image with a pinned tag (no `latest`), no secrets or `.env` copied in, `.dockerignore` keeping out `.git`, `.venv`, `node_modules`, `__pycache__` and `.env`, and the smallest sensible image (for example a `-slim` tag).
- Git rules from weeks 3-6:
  - make a branch before Claude writes anything
  - never change `main`
  - push and open a PR, read Files changed, merge on GitHub, then pull
  - the repo stays private
  - plain "Yes" for git prompts
  - "No" to `reset --hard`, `--force`, `git clean` and `rm -rf`
- Docker safety: "No" to `docker system prune -a`, `--privileged`, and mounting your whole home folder. Students run the cleanup commands themselves, only as shown.
- Every fact comes from the fact sheet with its URL. Anything not observed is marked "being tested". Pin the versions tested.
- No em dashes (U+2014) or en dashes (U+2013). The rubric is a table under `## Rubric` with points in the last column, totalling 10.
- `example-project/` stays the labelled instructor example. It passes `scripts/check_course.py`, and its tests run with `python3 -m unittest` both on the host and in the container.
- Instructor-only material goes in the private repo.
- Branch `week-07-docker` in the course repo and `week-07` in the instructor repo. The user merges. Links come first, one bare URL per line.

## Review Focus

1. **The interactive program hangs or exits in the container.** Running it without `-it` means `input()` gets end-of-file. The deal screener exits with "Stopped before all the numbers were typed." and code 1. The README uses `docker run -it --rm`, and troubleshooting explains the message. Task 2 checks both the with and without `-it` behaviour for real.
2. **Secrets or junk get copied into the image.** If `COPY . .` runs without a `.dockerignore`, `.env`, `.git` and `.venv` go in. The deal screener's `.dockerignore` and a check (`docker run --rm <image> ls -a`) show what's inside. The README has students run the same check, and the `safe-and-private` review step covers it.
3. **On Windows the student runs `docker` in PowerShell, or Ubuntu integration is off,** so they see `docker: command not found` in Ubuntu. The install steps say exactly where to turn integration on, and troubleshooting covers the message, from Docker's WSL docs.
4. **The build fails or behaves differently on Apple chip vs Intel.** The official image is multi-architecture. The fact sheet checks the `python` slim tag's platforms, and the README says what to do if a package has no build for the chip.
5. **The disk fills up, or old images pile up.** The README shows `docker image ls` and `docker image prune` (student-typed, with a confirmation prompt, from the docs), and says how much space the install needs, from Docker's requirements.

### Task 2: Deal screener in a container (example-project)

**Files:**
- Create: `example-project/Dockerfile`, `example-project/.dockerignore`
- Modify: `example-project/README.md` (add a "How to run with Docker" section, and the week 7 state with tag `week-07` once published)

**Interfaces (quoted by the README and slides):**
- **Dockerfile:** 6-10 lines, each with a short plain-English comment above it.
  - `FROM python:<pinned>-slim` (the tag from the fact sheet, pinned to minor version, for example `3.12-slim`)
  - `WORKDIR /app`
  - `COPY . .`
  - `CMD ["python", "-m", "dealscreener"]`
  - No `pip install`, because the project uses only the standard library. The comment says so, and says where a `requirements.txt` line would go for projects that need packages.
  - Optionally a non-root `USER`, if the fact sheet supports it simply. Note the choice.
- **.dockerignore:** `.git`, `.venv`, `venv`, `node_modules`, `__pycache__`, `*.pyc`, `.env`, `.env.*`, `.claude`, `.superpowers`, `docs`, `REVIEW.md`. Each group gets a comment saying why. The README explains that `docs` and `REVIEW.md` are left out because the program doesn't need them.
- **Commands:**
  - Build: `docker build -t dealscreener .`, run inside `example-project/`.
  - Program: `docker run -it --rm dealscreener`.
  - Tests: `docker run --rm dealscreener python -m unittest`.

- [ ] **Step 1:** Write `.dockerignore`, then the `Dockerfile`.
- [ ] **Step 2:** Build. Record the build output summary and the image size (`docker image ls dealscreener`).
- [ ] **Step 3:** Run `docker run --rm dealscreener python -m unittest`. Expect `Ran 39 tests ... OK`.
- [ ] **Step 4:** Pipe listing A and listing B in with `printf '...' | docker run -i --rm dealscreener`. The outputs must match the host run byte for byte (diff them).
- [ ] **Step 5:** Check the image contents: `docker run --rm dealscreener ls -a /app` lists only the program's files, with no `.git`, `.claude`, `docs` or `__pycache__`. Record the listing.
- [ ] **Step 6:** Run `docker run --rm dealscreener` with no `-i`. Record that it prints "Stopped before all the numbers were typed." and exits with 1. That is the Review Focus 1 evidence for troubleshooting.
- [ ] **Step 7: Week 6 reviewer on the Dockerfile.** The controller runs the `safe-and-private` agent's instructions as a separate read-only subagent on `Dockerfile` and `.dockerignore`. Record the findings, triage them, and fix any Must fix. Record the review in `example-project/REVIEW.md` under a new `## Week 7: Dockerfile review` section, using the same table.
- [ ] **Step 8:** Update the example README. Run `python3 scripts/check_course.py` and check it prints OK. Check there are no dashes. Commit on `week-07-docker`.
